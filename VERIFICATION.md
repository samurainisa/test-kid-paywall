## Публичный сервис Railway

`node scripts/verify-live.mjs https://test-kid-paywall-production.up.railway.app` прошёл. Использованы отдельные тестовые cookie, созданы тестовые покупки без списания денег. Проверены health/SQLite, каталог тарифов, HTTPS-cookie Secure/HttpOnly/Lax, неверные запросы 400 с пустым восстановлением, одновременные повторы 201/200 с идентичной покупкой, конфликт 409 и изоляция нового браузера.

В настоящем браузере пройдены пять состояний, выбор месяца и стрелки radio, блокировка действий, ошибка сети и повтор с тем же requestId, настоящий успех после POST, игра и восстановление после reload. Шесть размеров из ТЗ не имеют горизонтального скролла; нижние действия доступны. Все шесть SVG и локальный шрифт отдаются с HTTP 200. Снимки сделаны после загрузки шрифта **и decode всех текущих изображений**, чтобы сетевое ожидание иконок не выглядело ошибкой вёрстки. Отсутствуют uncaught JS-ошибки и предупреждения гидратации; ожидаемый `net::ERR_FAILED` вызван тестовым перехватом POST.

Отчёт и снимки: `test-results/live/report.json`, `test-results/live/*.png`. Сохранённая тестовая сессия и исходная покупка находятся в игнорируемом `test-results/live/`; они используются для последующей проверки `--restore-only`. Прямое чтение SQLite на Railway агенту недоступно; такое чтение проведено локально и в Docker, а публичная запись подтверждается ответом purchase и восстановлением той же записи. Восстановление после завершённого нового Railway deployment будет проверено отдельно.

## Сервер и хранение

`npm run typecheck`, `npm run build`, `npm test` прошли. Nuxt 4.6.1, Nitro 2.13.4, Vue 3.5.44, Node 22.23.1. Тест запускает **скопированную самостоятельную production-сборку** из временного каталога, с отдельной SQLite. Рабочую БД не удаляет и не заполняет. Проверены:

- Два тарифа GET, создание/замена UUID-cookie, HttpOnly, Lax, path и Secure через HTTPS-forwarded header.
- Неверный тариф, тело, UUID и повреждённый JSON: 400 и отсутствие INSERT.
- Одновременные POST с одним ключом: 201/200, одна строка; другой тариф с этим ключом: 409.
- Цена, устройство и дата определяются сервером; сохранённая строка прочитана напрямую через SQLite.
- Restore возвращает свою запись; свежий браузер не видит чужую. Отсутствующая покупка и ошибка restore сохраняют выбор.
- Ошибки GET/POST, повтор загрузки, снятие блокировки действий в finally.
- Настоящий отказ INSERT через временный SQL-trigger: 500, ноль новых строк, успех не показывается. Trigger существует только в тестовой БД и удаляется тестом.
- Ответ намеренно теряется **после настоящего COMMIT**: повтор UI использует исходный requestId, получает 200 и не добавляет строку.
- Новый процесс, другой каталог релиза, тот же SQLite-файл: строки и восстановление сохранены. Это локальная имитация redeploy, а не проверка Railway.

`docker build` и `npm run test:docker` также прошли. В Linux-образе проверена загрузка нативного `.node`, health, настоящая покупка и непосредственное чтение `/data/paywall.sqlite`. Контейнер удалён и создан заново с тем же именованным volume: идентичная запись, восстановление с cookie и повтор операции сохранены. `test-results/docker-report.json` содержит имя сохранённого **тестового** volume. Отдельный Compose-сервис запущен на `http://localhost:3000` с рабочим именованным volume; автоматические тесты используют отдельные БД и не удаляют рабочие записи.

## Экран и сравнение

`test-results/comparison.html` показывает эталон, реализацию, наложение 50/50 и diff для каждого состояния. `report.json` содержит геометрию, типографику и результаты; `<state>.png`, `<state>-overlay.png`, `<state>-diff.png` доступны отдельно.

## Адаптация и ограничения проверки

Проверены 360×800, 375×812, 390×844, 414×896, 430×932, 360×640 и дополнительно 320×640. На каждом размере пройдены ошибка покупки, реальный успех и переход в игру; нет горизонтального скролла/наложения сообщения и кнопки, нижние действия доступны через вертикальный скролл. Hero остаётся 358×144, кнопки закрытия/restore имеют зоны 44 px; radio работает стрелками. Отдельный тест текста 200% на 360×640 подтверждает рост страницы и доступность действий (`mobile-large-text.png`). Проверка браузерная, физический телефон/Safari не проверены.

В штатном сценарии нет uncaught JS-ошибок и предупреждений гидратации, серверные импорты отсутствуют в клиентском JS. Намеренно оборванные запросы пишут ожидаемый `net::ERR_FAILED`; это отражено в `report.json`. При отказе SQL сервер пишет диагностический лог, пользователю показывается только понятное сообщение.
