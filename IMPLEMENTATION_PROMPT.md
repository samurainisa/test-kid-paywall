# ТЗ и промпт для агента: TestKidTask, Nuxt 4 + SQLite

Ты реализуешь учебное тестовое задание целиком: мобильный экран покупки полного доступа к условной детской игре, серверные обработчики, запись покупки в SQLite, проверки и подготовку размещения.

Действуй самостоятельно до рабочего результата. Не останавливайся на плане или каркасе. Дизайн уже готов, заново его не придумывай. Ориентир на всю работу: два часа. При нехватке времени сохраняй основной сценарий, сервер и постоянную БД; упрощения честно опиши в README. Не заявляй о выполненных проверках, которых не проводил.

## 2. Стек и ограничения

- Nuxt строго версии 4.x, стабильная версия, без nightly; закрепи фактическую версию файлом блокировки зависимостей
- Vue 3, Composition API, TypeScript, script setup
- обычный CSS с переменными и scoped-стилями; SCSS допустим, если уже есть в проекте
- SQLite через better-sqlite3 и типы @types/better-sqlite3
- один проект, фронт в app/, сервер в корневой server/
- npm и package-lock.json, если в существующем проекте не выбран другой менеджер
- Node.js 22 с актуальным исправлением, одинаковая версия при сборке и запуске
- серверная сборка node-server
- интерфейс и сервер должны работать на одном домене

Не добавляй Pinia, библиотеку интерфейса, Tailwind, ORM, авторизацию, административную панель или отдельный сервер без необходимости. Здесь достаточно небольшого composable и Vue-состояния. Не используй реальный платёжный SDK, деньги или ключи платёжных систем. Не заменяй SQLite облачной базой, памятью или localStorage. Не используй весь снимок экрана в качестве интерфейса.

Точное визуальное сравнение проводи на 390 × 844, deviceScaleFactor=1, без встроенных дополнительных полей устройства.

Правила:
- основная область width:100%, max-width:430px, margin-inline:auto
- фон всей страницы #F7F7FF
- 16 px боковых отступов на всех ширинах 360–430
- ширины содержимого: 328 на 360, 343 на 375, 358 на 390, 382 на 414, 398 на 430
- высоты карточек 96, зазор 16, кнопка 56, зоны закрытия/восстановления 44
- все карточки и кнопки занимают доступную ширину
- сохраняй размеры шрифтов и значков
- hero имеет естественную ширину 358 и центрируется в доступной области
- подписи цен не переносятся, название получает оставшуюся ширину
- верхняя часть и строки не обрезаются, текст увеличивает высоту при необходимости
- основной заголовок допускает естественное изменение переносов
- резерв сообщения сохраняет минимум 72 px
- по умолчанию экран имеет min-height:844px; при низкой высоте viewport используй обычный вертикальный скролл
- на высоких экранах min-height:max(844px,100dvh), свободное место можно добавить в резерв перед покупкой; при 844 точная базовая геометрия сохраняется
- не фиксируй кнопку поверх контента, не используй body overflow:hidden
- при увеличенном шрифте или дополнительной строке содержимое растёт, скролл остаётся доступным
- для safe-area используй env(safe-area-inset-top/bottom) дополнительно к базовым 16 px. При нулевых inset эталон не должен сдвигаться
- meta viewport: width=device-width, initial-scale=1, viewport-fit=cover
- ширины ниже 360 поддержи без горизонтального скролла по возможности; обязательные проверки 360–430
- на больших экранах покажи тот же мобильный интерфейс по центру, без новой настольной версии

Не растягивай весь экран transform:scale. Не добавляй рамку телефона, статусбар или искусственную панель браузера.

## 9. Получение данных и состояние Vue

Общие типы:
- Offer: id ('monthly'|'yearly'), title, period ('month'|'year'), priceMinor, currency ('RUB'), months, recommended
- PurchaseResponse: id, offerId, createdAt, deviceId, test:true
- RestoreResponse: found:boolean, purchase:PurchaseResponse|null

Цены храни целыми копейками:
- monthly: 29900
- yearly: 199000

Показатель 166 ₽ в месяц для года: округление 1990/12 до целого; не записывай его как фактическую месячную цену оплаты.

GET /api/offers возвращает { offers: Offer[] }, список ровно из двух тарифов.
Источник тарифов один на сервере. На фронте нет дублирующего каталога с ценами.
На сервере проверяется выбранный offerId по этому каталогу.

Используй useFetch('/api/offers', {server:false,lazy:true}) либо эквивалентное клиентское получение с корректным состоянием. Для первого показа считай idle и pending состояниями загрузки, если данных ещё нет.
Мутации покупки/восстановления выполняй через $fetch в обработчиках, не через наблюдатель, который может случайно повторить POST.

Состояния раздельные:
- offersStatus и offersError
- selectedOfferId
- operation: 'idle'|'purchase'|'restore'
- operationError
- purchaseResult

После первого успешного GET выбери yearly. При обновлении тарифов сохрани допустимый текущий выбор.
Во время любой мутации остальные действия блокируются.
При ошибке finally возвращает возможность действий.
Не обращайся к window/localStorage при серверном рендеринге.
Отключи автоматические повторные POST либо явно укажи retry:0; повтором управляет пользователь.

## 10. Сервер и идентификатор устройства

Файлы методов .get.ts/.post.ts. Используй доступные в установленной версии Nuxt серверные помощники и проверь их по документации.

Условный идентификатор устройства: UUID, созданный сервером и сохранённый в cookie paywall_device.
- HttpOnly, SameSite=Lax, path='/'
- срок например 365 дней
- Secure только при HTTPS
- существующее значение проверяй на формат UUID, неверное замени
- в этом учебном сценарии cookie не является полноценной авторизацией
- источник deviceId для операций: cookie, не произвольное поле из тела запроса
- GET offers создаёт cookie при первом посещении
- restore при её отсутствии создаёт новый ID и возвращает found:false
- не используй IP, отпечаток устройства или личные данные

Это восстановление покупки в том же браузере/webview с сохранённой cookie. Между устройствами или после удаления cookie восстановление не предусмотрено; честно опиши это ограничение в README.

POST /api/purchase принимает {offerId,requestId}, оба проверяются.
requestId: UUID операции, созданный клиентом.
Цена, дата, deviceId и итоговый статус определяются сервером.
Некорректные данные: HTTP 400, неизвестный тариф: HTTP 400 или 404, конфликт requestId: HTTP 409, ошибка записи: HTTP 500.
Успешный ответ только после завершённого INSERT/COMMIT.
Новый результат: HTTP 201; повтор существующей операции: HTTP 200 с той же покупкой.

Защита от повторов:
- перед запросом заблокируй кнопку
- уникальность (device_id,request_id) в БД
- повтор того же ключа и тарифа возвращает исходную запись
- тот же ключ с другим тарифом возвращает 409
- при сетевой неопределённости сохраняй requestId для повторной попытки того же тарифа
- при выборе другого тарифа начинается новый requestId
- после успешной покупки повторный POST интерфейсом недоступен

POST /api/restore не создаёт покупку. Читает последнюю запись текущего deviceId.
При наличии: {found:true,purchase:...}, экран успеха.
При отсутствии: {found:false,purchase:null}, сообщение «Покупок для этого устройства пока нет», остаёмся на выборе тарифов.
Ошибка восстановления не должна стирать текущий выбранный тариф.
Не открывай общий список чужих покупок публичным API.

GET /api/health: минимальный статус сервиса и работоспособности БД, например SELECT 1, без путей файлов и содержимого таблиц.

## 11. SQLite

Одна таблица purchases достаточно:
- id TEXT PRIMARY KEY, серверный UUID
- offer_id TEXT NOT NULL
- device_id TEXT NOT NULL
- request_id TEXT NOT NULL
- price_minor INTEGER NOT NULL CHECK(price_minor > 0)
- currency TEXT NOT NULL
- created_at TEXT NOT NULL, UTC ISO 8601
- UNIQUE(device_id,request_id)
- индекс по (device_id,created_at)

offerId в HTTP и offer_id в SQL допустимы как разные представления одного поля. Схему явно создай SQL-командой CREATE TABLE IF NOT EXISTS и CREATE INDEX IF NOT EXISTS. Без удаления существующей таблицы при старте. Укажи schema version либо оставь одно простое начальное создание для учебного решения.

Подключение:
- путь из переменной SQLITE_PATH
- локально ./data/paywall.sqlite
- на платформе /data/paywall.sqlite
- создай родительский каталог
- одно лениво созданное подключение на серверный процесс
- подготовленные запросы, параметры вместо конкатенации SQL
- timeout 5000 ms
- для мини-сервиса достаточно обычного журналирования SQLite; WAL не обязателен. Если включаешь WAL, весь каталог вместе с .sqlite-wal/.sqlite-shm должен быть постоянным, а файловая система подходящей для этого режима
- транзакционная проверка повторного requestId и запись, например синхронная transaction(...).immediate()
- внутри синхронной транзакции better-sqlite3 не должно быть await

Создавай БД во время запуска или первого серверного запроса, не во время сборки. Не добавляй тестовую покупку при инициализации.

.gitignore/.dockerignore исключают data/, *.sqlite, *.sqlite-wal, *.sqlite-shm, .env, node_modules, .nuxt, .output, временные результаты тестов. Схема хранится в коде, фактическая БД не в Git и не в public/.

Не подменяй серверную запись клиентским состоянием. Проверка результата должна включать реальное чтение SQLite.

## 12. Размещение

Целевое решение: Railway, сервер Node.js и постоянный volume /data. SQLite остаётся обычным локальным файлом.
Если есть доступный существующий сервер с постоянным диском, можно использовать его вместо Railway и точно описать это в README.

Railway:
- сервис собирает Nuxt, запускает node .output/server/index.mjs
- постоянный volume подключён к тому же сервису с mount path /data
- SQLITE_PATH=/data/paywall.sqlite
- NODE_ENV=production
- NITRO_PRESET=node-server при сборке
- NITRO_HOST=0.0.0.0
- слушай PORT, который назначает платформа
- одна реплика/один серверный процесс
- проверка /api/health
- публичный HTTPS-домен

У Railway пробный доступ зависит от аккаунта, кредитов и срока. Перед размещением проверь доступность volume. Не обещай вечную бесплатную работу. Не оформляй платный тариф без указания пользователя. Если нет доступа к аккаунту, полностью подготовь проект, Dockerfile и команды, затем сообщи конкретный оставшийся шаг. Не выдавай подготовку за реальный деплой.

Dockerfile: используй совместимые стадии сборки и запуска на node:22-bookworm-slim. Проверь, что better-sqlite3 и его нативный .node действительно попали в серверную сборку и загружаются после запуска. Если требуется компиляция, установи инструменты только на этапе сборки. Не переноси node_modules с macOS в Linux. Запусти production-контейнер локально и проверь API, запись и сохранение после пересоздания с тем же volume.

Для проверки локального хранения через Docker можно добавить compose.yaml с именованным volume в /data. Это допустимое вспомогательное средство, не замена публичной ссылки.

НЕ используй nuxt generate, чисто статический хостинг или запись SQLite в /tmp как итоговое размещение. Не заменяй постоянный volume строкой VOLUME в Dockerfile: на платформе хранилище нужно действительно подключить.

## 13. Проверки

Не пиши большой набор тестов ради количества. Приоритет: реальные запросы, запись и восстановление, затем точность экрана.

Обязательные:
1. Проверка TypeScript и production-сборка.
2. Запуск собранного сервера, не только режима разработки.
3. GET offers возвращает два реальных тарифа.
4. Выбор месяца меняет выделение и текст кнопки; цена годовой карточки не меняется.
5. POST purchase записывает строку с offerId, временем и устройством.
6. Неверный offerId и некорректный запрос ничего не записывают.
7. Два одинаковых requestId дают одну строку; другой тариф с тем же ключом даёт конфликт.
8. Restore читает запись с cookie; новый браузер не видит чужую покупку.
9. Ошибка сети показывает сообщение, кнопки снова доступны.
10. Успех нельзя показать при неудачной записи.
11. После перезапуска production-сервера и повторного размещения запись восстанавливается из того же постоянного диска.
12. В консоли нет ошибок, серверных импортов в клиенте и предупреждений гидратации.

Для API используй отдельную временную БД в тестах. Тесты не должны удалять рабочую БД.
Для проверки сохранности: покупка → проверка строки → остановка процесса → новый процесс с тем же SQLITE_PATH → восстановление по той же cookie.

### Визуальные проверки

Используй Playwright или доступный браузер.
Эталонные изображения reference/*.png служат только для сравнения, не для вставки в интерфейс.
Проверь основной экран и все четыре состояния на 390 × 844. Сделай снимки после document.fonts.ready.
Для задержки и ошибки перехватывай GET/POST в браузерном тесте. Для успеха используй реальный POST в отдельной тестовой БД. Если ради точного снимка состояния используется тестовый ответ, дополнительно отдельно пройди настоящий сценарий сервера.
Не добавляй случайные ошибки, скрытые production-параметры покупки или постоянный таймер задержки ради этих состояний.

Сделай наложение или изображение различий между реализацией и эталоном. Проверь:
